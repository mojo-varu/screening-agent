# HR-агент отбора кандидатов — «Акватория»

## Что делает проект

Детерминированный движок отбора по трём вакансиям (BA, Fullstack, UX/UI) с
полной трассировкой решения: почему кандидат взят / в резерве / отклонён, по
какому именно критерию, и с какой заземлённой (проверяемой) цитатой-основанием
из резюме — не просто «модель сказала», а «вот эта строка резюме, вот её
позиция в тексте».

Решение (`берём` / `в резерв` / `отказ`) принимает не LLM, а детерминированное
правило поверх структурированных данных (`domain/decision.py`) — этот модуль
никогда не видит сырой текст резюме и никогда не вызывает LLM. LLM участвует
только в двух местах: определение подходящей вакансии по тексту резюме
(`classify_role`) и извлечение полей по жёсткой схеме (`extract_candidate`) —
оба в `extractors/`.

**Рабочий пайплайн — это `screen.py`**: одно резюме на входе → живой LLM →
детерминированный движок → объяснение на выходе (см. «Быстрый старт» ниже).
Отдельно в репозитории есть демо/тестовая инфраструктура вокруг
вручную размеченного набора из 10 резюме (`report.py`,
`fixtures/candidates_golden.json`) — она в `screen.py` и живой путь вообще
не используется; что это такое и зачем — специально отдельный, прозрачный
раздел «Golden-набор: что это и для чего» ниже, не просто строчка в списке.

Архитектурный принцип и его целевое состояние (что уже построено, что ещё
план) — в `TECH_ARCHITECTURE.ru.md` / `TECH_ARCHITECTURE.en.md`. Этот файл —
про то, как запустить, какие есть допущения и что пока не решено.

## Статус и ограничения

- 37 `pytest`-тестов, все проходят: регрессия на ручную разметку 10
  резюме (что это значит и почему не «ответы из задания» — см. «Golden-набор:
  что это и для чего» ниже), стоп-факторы как вето, регрессия на два реальных
  бага, явные acceptance-тесты на evidence-grounding (заземление цитат,
  судья по релевантности, штрафы на пустой evidence).
- Evidence-grounding (заземление цитаты в исходном тексте + проверка типов)
  построено и покрыто тестами. Судья по релевантности («доказывает ли эта
  цитата именно этот критерий») реализован, но включается только флагом
  (`--judge-relevance`), не в пути по умолчанию. Проверка согласованности
  evidence МЕЖДУ полями не реализована вообще. Подробный разбор целевой
  архитектуры и что из неё уже построено — `TECH_ARCHITECTURE.*.md`.
- Четыре LLM-провайдера реализованы и живьём протестированы: Ollama
  (self-hosted по умолчанию), Anthropic, Groq, Gemini — за одним интерфейсом,
  без SDK, только `urllib`/`curl`.
- Рендер отчёта (`.explain.md`) теряет часть детализации, которая есть в
  JSON — см. «Словарь статусов и потери при рендеринге» в «Известных
  проблемах» ниже, это первое, что стоит прочитать перед тем, как доверять
  меткам в `.explain.md` буквально.

## Требования

- **Python 3.9+** — сам движок использует только стандартную библиотеку.
- **pytest** — только для `tests/`; сам движок без него работает.
- Для локального провайдера — **Ollama**, установленный и запущенный.
- Для облачных провайдеров — ключ API (Anthropic и/или Groq и/или Gemini);
  ни один не обязателен, `--provider ollama` работает полностью offline.
- Не требуется: `pip install` каких-либо SDK провайдеров (`anthropic`,
  `google-generativeai`, `groq` и т.п.) — все четыре провайдера реализованы
  напрямую по HTTP (`extractors/providers.py`), SDK не используются нигде.

## Быстрый старт: облачные провайдеры

Положите ключи в `.env` в корне проекта (нужны только те провайдеры, которые
собираетесь использовать):

```
ANTHROPIC_API_KEY=...
GROQ_API_KEY=...
GEMINI_API_KEY=...
```

`.env` загружается автоматически (`extractors/providers.py`), в `.gitignore`
— никогда не коммитится.

Один живой прогон резюме через облачного провайдера:

```bash
python3 screen.py fixtures/resumes/R02.txt --provider gemini
python3 screen.py fixtures/resumes/R02.txt --provider anthropic
python3 screen.py fixtures/resumes/R02.txt --provider groq
```

Полный цикл: LLM определяет подходящую вакансию → LLM извлекает поля по
схеме роли → детерминированный движок решает → отчёт пишется в
`screening_results/R02.evidence.json` / `R02.explain.md`.

Опционально — судья по релевантности evidence (отдельный LLM-вызов на каждую
непустую цитату, не включён по умолчанию — см. «Известные проблемы»):

```bash
python3 screen.py fixtures/resumes/R02.txt --provider gemini --judge-relevance
```

## Команды для тестов

```bash
python3 -m pytest tests/ -v
```

37 тестов без сети и без LLM-вызовов (все на синтетических/golden-данных с
mock'нутыми вызовами модели там, где нужно):

- `tests/test_decisions.py` — golden-таблица решений по всем 10 кандидатам;
- `tests/test_stop_factors.py` — стоп-факторы как вето, а не ещё один
  must-have;
- `tests/test_missing_evidence.py` — регрессия на два реальных бага
  (`None` вместо `[]`/`0` от живой модели; `unclear` на чужой роли, который
  раньше ошибочно засчитывался как пройденный);
- `tests/test_validation.py` — явные acceptance-тесты evidence-grounding:
  офсеты заземляются точно (`cv_text[start:end] == text`, проверено на всех
  46 evidence-span в golden-наборе), фабрикация цитаты ловится и понижает до
  `unclear`, эскалация не выполняется без реально другой модели, confidence
  не может «вылечить» пустой evidence, судья по релевантности понижает
  реальные найденные случаи (не синтетические — размечены в самом
  golden-наборе).

Детерминированный golden-прогон (`python3 report.py`, см. «Результаты» ниже)
— второй, более медленный способ проверки: 10 решений, которые можно сверить
глазами по `report.md`.

## Результаты (выходные файлы)

**`python3 report.py`** — batch-прогон по 10 golden-кандидатам, без LLM:

- `report.md` — сводная таблица по всем 10;
- `screening_results/<id>.evidence.json` — полный артефакт по каждому
  кандидату (extraction → criteria → decision → validation, один JSON);
- `screening_results/<id>.explain.md` — то же самое, отрендеренное в
  читаемый вид (рендерится ИЗ этого JSON, не из отдельных живых объектов —
  так `.md` и `.json` не могут разойтись, но рендер теряет часть деталей,
  которые есть в JSON — см. «Словарь статусов и потери при рендеринге»);
- `evidence_full_matrix.json` — кросс-прогон всех 10 кандидатов через все 3
  роли (зачем — см. «Правила решения и допущения» → «Кросс-проверка ролей»).

**`python3 screen.py <resume.txt> --provider ...`** — один живой прогон,
пишет те же `screening_results/<id>.evidence.json` / `<id>.explain.md`
(общий рендерер с `report.py`).

**`python3 extract.py` / `python3 eval_extraction.py`** — Stage-1 по всем
резюме сразу и сравнение с golden (field/decision agreement) — для сравнения
провайдеров/моделей, не для повседневного использования.

## Golden-набор: что это и для чего

`fixtures/candidates_golden.json` — это НЕ ответы из задания и не внешний
эталон. Задание прямо говорит: *«Эталонного «правильного списка» в этом
файле нет: критерии задаёте вы»* — правильного списка не существует в
принципе, ни от куратора, ни откуда-либо ещё.

**Что это на самом деле:** 10 резюме из `02_вакансии_и_резюме.md`, вручную
размеченные мной в структурированные поля той же схемы, что использует
живой экстрактор (`FIELD_SPECS` в `domain/candidate.py`) — то есть мой
собственный разбор текста задания в JSON, ничем не отличающийся по статусу
от вывода LLM, кроме того, что размечен человеком один раз, а не моделью
при каждом запуске.

**Зачем это нужно, если это не «правильные ответы»:**

1. **Регрессия.** 37 `pytest`-тестов проверяют, что `engine/`+`domain/` не
   меняют поведение непреднамеренно при правках кода — сравнивая решение
   движка с решением ПО ТОЙ ЖЕ РАЗМЕТКЕ, а не с какой-то внешней истиной.
   Это ловит «я поменял `combine_worst()` и решение R10 тихо изменилось»,
   а не подтверждает, что R10 «должен» быть РЕЗЕРВ в каком-то абсолютном
   смысле.
2. **Детерминированное демо без LLM.** `python3 report.py` показывает
   решение движка за секунды, без сети, без ключей — полезно, чтобы увидеть
   логику отбора в действии, не дожидаясь живого вызова модели.
3. **Замер качества экстракции.** `eval_extraction.py` сравнивает, что
   LLM извлекла из сырого текста, с тем, что вручную извлёк я — это
   метрика того, «насколько экстрактор совпадает с моей ручной разметкой»,
   а не «насколько кандидат хорош».

**Что это НЕ делает:** не используется рабочим пайплайном `screen.py`
вообще (проверено — `grep` по всему репозиторию подтверждает, что
`screen.py` не импортирует и не читает `candidates_golden.json` ни в каком
виде) и не является утверждением о том, что какой-то из 10 кандидатов
«на самом деле» должен получить конкретное решение — это была бы
переоценка того, что 10 pytest-тестов вообще способны доказать.

`poc.py` — тот же принцип: минимальный скрипт, которым я один раз вручную
проверил, что живой Ollama действительно возвращает валидный JSON по схеме,
до того как строить полный `extract.py` поверх этого предположения. Ничего
в репозитории его не импортирует (проверено `grep`), он не участвует ни в
`screen.py`, ни в тестах, ни в `report.py` — это разовый диагностический
артефакт разработки, не часть пайплайна.

## Правила решения и допущения

### Модель критериев

Для каждой вакансии (`fixtures/vacancies/roles.json`) заданы:

- **must-have** — обязательные критерии. «Жёсткий» провал (explicit false,
  подтверждённый цитатой) → `отказ`.
- **стоп-факторы** — явные несовместимости из ТЗ («только Java enterprise без
  веба» и т.п.), отдельный от критериев тип (`StopFactorResult`). Срабатывание
  любого → `отказ`, даже если все must-have формально закрыты.
- **nice-to-have** — не влияют на решение, только информация для человека.
- **вилка зарплаты** — не стоп-фактор, отдельный флаг: `in_range` /
  `above_range` / `below_range` / `unknown`. Выше вилки при отсутствии других
  проблем → `в резерв`; ниже вилки — видимый сигнал, но не блокирует решение.

### Статус критерия и evidence-grounding

Каждый критерий: статус `met` / `not_met` / `unclear` / `not_applicable`,
плюс обязательные `reason` и `provenance` (каким механизмом получен статус).

**Ключевое правило:** критерий может получить `met` или `not_met` только если
у него есть цитата, реально найденная в тексте резюме (точные символьные
офсеты, `raw_text[start:end] == текст цитаты`). Нет цитаты или она не
находится дословно — критерий честно `unclear`, не угадывается молчаливо.
`unclear` внутри заявленной профессии кандидата **не блокирует** `берём`
(решение принимается, но с пониженной уверенностью и явным списком
неподтверждённого). `partial`-сигнал (bool3-значение, например «интеграции
делегировала архитектору») даёт статус `not_met` с пометкой в `provenance`
(`rule:partial_signal`) — это «мягкий» провал (→ `в резерв`), отличается от
«жёсткого» `not_met` с `provenance=rule:explicit_false` (явное опровержение
→ `отказ`). Статус — всегда одно из четырёх значений; «мягкий» vs
«жёсткий» — это `provenance`, не отдельное пятое значение статуса (и это
как раз то, что теряется при рендере — см. «Известные проблемы»).

### Кросс-проверка ролей

`evidence_full_matrix.json` прогоняет каждого кандидата через все три
вакансии. `unclear` на чужой профессии не даёт молчаливого прохода —
`domain/decision.py` с `cross_role=True` отклоняет такого кандидата, не
переобозначая статус критерия (у BA-резюме действительно нет опровергающей
цитаты про TypeScript — её там просто нет, но и подтверждающей тоже нет).
Без этого разделения резюме бизнес-аналитика формально проходило бы
must-have Fullstack и UX/UI просто потому, что для чужой профессии в резюме
нет отрицательных сигналов — их там нет вообще никаких.

### Разбор спорных случаев (на 10 размеченных резюме)

- **R03 (Анна Ким, BA, 300к при вилке 220–280к, интеграции «обычно отдавали
  архитектору»)** — сильный кандидат по домену и требованиям, но
  `integrations` — мягкий `not_met`, и зарплата выше вилки → `в резерв`.
- **R10 (Никита Фролов, fullstack, сильный LLM-agent опыт, сам пишет «фронт
  рабочий, не премиальный»)** — по стажу и стеку проходит, но
  `frontend_quality` — мягкий `not_met` по собственному признанию → `в
  резерв`: сильный nice-to-have не компенсирует ослабленный must-have.
- **R05 (Елена Жукова, frontend, готова летать в Москву за счёт компании)** —
  `stack` и `frontend_quality` — жёсткий `not_met` (явно не настраивала SSR,
  стек без TS/Python на боевых задачах) → `отказ`, формат работы вторичен.
- **R06 (Павел Чернов, 12 лет Java, хочет «перейти во fullstack»)** —
  срабатывают два независимых стоп-фактора (`java_enterprise_only`,
  `no_releases`) → `отказ`, оба перечислены в trace, не только первый.
- **R09 (Юлия Рахманова, 10 лет графического дизайна, Figma «освоила год
  назад», UX-кейсов нет)** — движок явно отличает «10 лет в дизайне» от «лет
  именно в UX/UI» (для R09 — `0`), плюс стоп-фактор `graphic_design_only`.

### Допущения

- **Семантика решений**: `берём` = все must-have не провалены и не частичны,
  стоп-факторов нет; `в резерв` = мягкий провал хотя бы одного must-have ИЛИ
  зарплата выше вилки, без жёстких провалов и стоп-факторов; `отказ` =
  жёсткий провал хотя бы одного must-have ИЛИ сработал стоп-фактор.
- **Зарплата выше вилки — не стоп-фактор** (в ТЗ это не названо причиной
  отказа); ниже вилки — тоже не блокирует, только видимый сигнал.
- **`unclear` не блокирует `берём` внутри своей профессии**, но блокирует на
  чужой роли при кросс-прогоне — осознанное, тестируемое допущение.
- **Evidence обязателен для `met`/`not_met`**: значение без заземляемой
  цитаты — `unclear`, не принимается на веру по одной заявленной уверенности
  модели, включая случай, когда эскалация вернула высокую confidence, но
  цитаты так и не дала.
- **Нет ограничения на число кандидатов в шортлисте** — решение по каждому
  независимо по правилам, не под квоту.
- **Маршрутизация резюме по вакансии**: для golden-набора (`report.py`) роль
  берётся из `primary_role` в fixtures; для произвольного резюме
  (`screen.py`) — живой дешёвый LLM-классификационный проход перед основной
  экстракцией.
- **Эскалация требует реально другую модель** — если для провайдера настроена
  одна и та же модель на «cheap» и «strong» (сейчас так для всех четырёх
  провайдеров), эскалация явно отключается и это фиксируется в выводе, а не
  тихо превращается в повторный запрос к той же модели.

### Совмещение ролей

Кандидат может рассматриваться на две роли, если это явно обосновано данными
резюме. В этом наборе такого случая не нашлось — каждый оценён только на
свою основную специализацию.

## Известные проблемы

### Словарь статусов и потери при рендеринге

Движок различает четыре статуса критерия — `met`, `not_met`, `unclear`,
`not_applicable` — но `not_met` дополнительно различается по `provenance`:
«жёсткий» (`rule:explicit_false`, явное опровержение) и «мягкий»
(`rule:partial_signal`, bool3-значение `partial` — evidence подтверждает
часть критерия и явно ограничивает остальное). Это разделение есть в JSON
(`criteria.must_have[].provenance`), но НЕ в рендере `.explain.md` — там оба
случая показаны одной и той же меткой «не выполнено».

Три следствия при чтении отчёта:

1. **`partial` на must-have — это мягкий провал**, ведущий к РЕЗЕРВ, а не к
   ОТКАЗ — рендер печатает его как «не выполнено», что выглядит строже, чем
   есть на самом деле (R03 — интеграции, R10 — качество фронтенда).
2. **Критерий с меткой «нет цитаты» может иметь заземлённые под-поля.**
   `git_deploy` у R10 — `unclear`, потому что Git и код-ревью не подтверждены
   цитатой; при этом `deploy` подтверждён явно («Деплой на VPS.») — но эта
   цитата и сам факт `met` для `deploy` полностью пропадают из
   агрегированного критерия: `combine_worst()` в `engine/rules.py` берёт
   evidence и reason только от под-сигналов с ХУДШИМ статусом, а `deploy`
   там не худший. Проверено на реальном golden-прогоне R10:
   `evidence: []`, `reason` вообще не упоминает `deploy`, хотя цитата лежит
   прямо рядом, в блоке `extraction.deploy_evidence`.
3. **`compensation_status` — это факт, а не пункт для уточнения** — он
   влияет на решение только через явное правило (`above_range` → максимум
   РЕЗЕРВ, не более).

**Известный пробел:** переиспользование одной цитаты для нескольких
критериев не обнаруживается. Живой прогон Gemini на R05 процитировал «SSR не
настраивала, формы отправляла в Formspree» сразу для четырёх полей, включая
`deploy`, о котором эта фраза не говорит вообще ничего. На итоговое решение
это не влияет (отказ и так опирается на `stack` и `frontend_quality`), но
`git_deploy` в этом случае честнее было бы показать как `unclear`, а не
`not_met` — сейчас же неверно приписанная, но формально заземлённая цитата
даёт критерию статус «жёсткого» провала, которым он на самом деле не
является. Проверено на реальном выводе (`screening_results/R05.evidence.json`
из живого прогона): `status: not_met`, `provenance:
combine:worst(...,rule:explicit_false)`, evidence — та самая неточная
цитата. Ловит такие случаи только cross-field consistency check, которого
пока нет (см. `TECH_ARCHITECTURE.*.md`).

### Харнесс оценки экстрактора — сознательно минимальный

`eval_extraction.py` считает только field-level и decision-level agreement
против вручную размеченного набора — ничего сложнее. На потоке реальных
резюме имеет смысл заменить его на готовый фреймворк оценки LLM (например
DeepEval или аналог), а не растить свой. Важная оговорка: это решает задачу
измерения качества экстракции НА ДАТАСЕТЕ, а не задачу «подтверждает ли эта
конкретная цитата этот конкретный критерий» — второе по-прежнему остаётся
задачей судьи по релевантности внутри пайплайна (`validation/relevance.py`),
не харнесса оценки.

### Остальное

- **Модель не всегда детерминирована между одинаковыми вызовами.** Повторные
  прогоны одного резюме через один провайдер давали разные наборы evidence и
  разную уверенность (temperature=0 не гарантирует битовую повторяемость у
  всех провайдеров) — итоговое решение при этом оставалось стабильным во
  всех наблюдавшихся повторах, но состав подтверждающих цитат может
  отличаться от запуска к запуску.
- **Эскалация сейчас — механизм для будущего, не для сегодня.** Для всех
  четырёх сконфигурированных провайдеров «cheap» и «strong» — одна и та же
  модель, поэтому эскалация не даёт прироста качества, только честно
  фиксирует, что поле осталось неуверенным (`_needs_human_review`). Код для
  настоящей эскалации есть и протестирован (mock-сценарий в
  `tests/test_validation.py`); реального прогона на действительно другой
  модели не делали.
- **Качество извлечения заметно зависит от провайдера/модели.** На 10
  размеченных резюме `phi4-mini:3.8b` дал более высокое decision-level
  agreement, чем `qwen2.5:3b`, и заметно меньше галлюцинировал
  стоп-факторов — поэтому он выбран моделью по умолчанию для Ollama.
- **Groq изредка блокировался на уровне сети** в песочнице, где вёлся
  разработка (Cloudflare client-fingerprint блокировка на
  `urllib.request`; решено обходом через системный `curl` в
  `extractors/providers.py`) — если вы видите HTTP 403 "Access denied.
  Please check your network settings" от Groq на своей машине, это тот же
  класс проблемы, а не баг в коде.
- **Блок-требование «Москва, гибрид, 2–3 дня в неделю» проверяется только
  частично.** Оно указано в задании один раз, для всех трёх вакансий сразу,
  но в критериях есть только его узкий частный случай — стоп-фактор
  `remote_other_tz` у V1 («100% удалёнка из ДРУГОГО часового пояса без
  гибрида»). Для V2 и V3 нет вообще никакой проверки формата работы —
  ни must-have, ни стоп-фактора. Ни на одно из 10 решений это не повлияло
  (самый близкий случай, R06 с «только офис, 5/2», и так отклонён по двум
  независимым стоп-факторам), но критерий из задания реально не покрыт кодом
  для V2/V3 — это не забытая мелочь, а осознанно незакрытый пробел, который
  стоит явно обсудить, а не тихо чинить произвольным решением.

## Структура репозитория

Рабочий пайплайн (это и есть продукт):

```
domain/        чистые данные + role-agnostic правила
                (Vacancy, CandidateProfile, CriterionStatus, EvaluationResult,
                 decision.py — ЕДИНСТВЕННОЕ место, где принимается решение)
engine/        ролеспецифичные критерии (какие поля резюме смотреть для
                BA/Fullstack/UX-UI) + build_criterion() — точка, где сырое
                значение + evidence-цитата становятся CriterionResult
extractors/    единственный слой, которому разрешено вызывать LLM
                (providers.py — 4 провайдера за одним интерфейсом;
                 llm_extractor.py — промпты, эскалация, кеш)
validation/     заземление цитат в исходном тексте (grounding.py) и
                LLM-судья по релевантности (relevance.py) — см.
                TECH_ARCHITECTURE.*.md, "Evidence validation"
fixtures/vacancies/   критерии вакансий (V1/V2/V3) — источник для must-have/
                nice-to-have/стоп-факторов, из 02_вакансии_и_резюме.md
fixtures/resumes/     10 сырых резюме (.txt) — вход для screen.py и извлечения

screen.py      CLI: одно резюме -> LLM -> движок -> отчёт (РАБОЧИЙ ПУТЬ)
```

Демо / регрессия / замер качества экстракции — НЕ используются `screen.py`
(подробно — «Golden-набор: что это и для чего» выше):

```
fixtures/candidates_golden.json   10 резюме, размеченные вручную мной —
                НЕ ответы из задания, их не существует (см. выше)
tests/         pytest — регрессия против ручной разметки + acceptance-тесты
                evidence-grounding
report.py      CLI: ручная разметка -> движок -> отчёт (batch, без LLM,
                детерминированное демо логики отбора)
extract.py     Stage-1 по всем резюме сразу: конкурентность, кеш, эскалация
poc.py         разовый диагностический скрипт из разработки — проверка, что
                живой Ollama отдаёт валидный JSON по схеме; ничего его не
                импортирует, не часть пайплайна
eval_extraction.py   сравнение LLM-экстракции с ручной разметкой
                (field/decision agreement) — метрика экстрактора, не
                кандидатов

environment.yml       conda-окружение (единственная зависимость — pytest)
TECH_ARCHITECTURE.*.md   целевая архитектура, что построено vs что план
```
